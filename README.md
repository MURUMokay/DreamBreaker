# DreamBreaker

Десктоп-приложение на Rust с использованием GUI-фреймворка [Iced](https://iced.rs/) и PostgreSQL через [sqlx](https://github.com/launchbadge/sqlx).

## Быстрый старт (для нового разработчика)

### 1. Установи зависимости

- [Rust](https://www.rust-lang.org/tools/install) (последняя стабильная версия)
- [PostgreSQL](https://www.postgresql.org/download/) (15+) — при установке запомни пароль пользователя `postgres`
- [VS Code](https://code.visualstudio.com/) с рекомендуемыми расширениями (предложатся сами)

Убедись, что команда `psql` доступна в терминале (папка `PostgreSQL\bin` должна быть в PATH).

### 2. Настрой БД одним кликом

Запусти **`setup.bat`** (двойной клик). Он создаст пользователя, базу, расширения и файл `.env`.
Введи пароль пользователя `postgres`, когда `psql` его запросит.

### 3. Играй

Запусти **`run.bat`** (двойной клик). Миграции применятся автоматически при первом запуске.

## Вспомогательные скрипты (.bat)

| Файл | Когда запускать | Что делает |
|------|-----------------|------------|
| `setup.bat` | Один раз при установке | Создаёт БД, пользователя, расширения, `.env` |
| `run.bat` | Каждый раз для игры | Запускает игру (`cargo run --release`) |
| `build.bat` | Перед показом/защитой | Собирает релизный `.exe` + кладёт рядом `.env` |
| `reset.bat` | При изменении схемы БД | Удаляет и пересоздаёт БД с нуля (с подтверждением) |

### Ручная настройка (если не используешь батники)

```sql
-- В psql под пользователем postgres:
CREATE USER dreambreaker WITH PASSWORD 'secret';
CREATE DATABASE dreambreaker OWNER dreambreaker;
\c dreambreaker
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";
CREATE EXTENSION IF NOT EXISTS "pgcrypto";
```

Затем скопируй `.env.example` в `.env` и запусти `cargo run`.

Миграции применятся **автоматически** при первом запуске — приложение само создаст таблицы.

## Миграции БД

Схема базы данных хранится в папке `migrations/` в виде SQL-файлов. Файлы названы по шаблону `<номер>_<описание>.sql` (например `7_properties.sql`) и применяются по возрастанию номера. Схема соответствует ER-диаграмме проекта.

### Как это работает

- Миграции **встроены в бинарник** во время компиляции (`sqlx::migrate!()` макрос)
- При запуске приложение применяет новые миграции автоматически
- sqlx ведёт служебную таблицу `_sqlx_migrations`, в которой отмечает применённые
- Откатывать миграции назад не нужно — добавляй новые файлы поверх

### Как добавить новую миграцию

Создай новый файл в `migrations/` со следующим по порядку номером:

```
migrations/14_new_feature.sql
```

И внутри напиши SQL:

```sql
ALTER TABLE properties ADD COLUMN level INT NOT NULL DEFAULT 1;
```

Закоммить файл в git — при следующем `cargo run` миграция применится у тебя и у всех остальных разработчиков автоматически.

**Важно:** не редактируй уже применённые миграции — sqlx запоминает их хеш и откажется работать при несовпадении. Только добавляй новые файлы. При работе вдвоём договоритесь, кто берёт какие номера, чтобы не было конфликтов.

### Опционально: sqlx-cli

Для удобной работы с миграциями можно поставить `sqlx-cli`:

```bash
cargo install sqlx-cli --no-default-features --features postgres
```

Тогда можно генерировать пустые миграции по шаблону:

```bash
sqlx migrate add описание_изменения
```

Это **не обязательно** — миграции применит само приложение.

## Структура проекта

```
DreamBreaker/
├── .vscode/              # Настройки VS Code (extensions, debug, tasks)
├── migrations/           # SQL-миграции БД (применяются автоматически)
```

## Запуск

```bash
cargo run                          # debug-сборка
cargo build --release              # релизная сборка
cargo test                         # тесты
cargo clippy --all-targets         # линтер
```

В VS Code: `Ctrl+Shift+B` для `cargo run` или `F5` для отладки.

## Архитектура

**Iced** построен на принципе Elm Architecture:

1. **State** (`DreamBreaker`) — состояние приложения
2. **Message** (`Message`) — события, описывающие изменения
3. **update** — изменяет состояние в ответ на сообщение
4. **view** — описывает UI на основе состояния

**Работа с БД** — асинхронная, через `Task::perform`. UI никогда не блокируется на запросах: задача уходит в `tokio`, а результат возвращается как `Message`.
